# Deribit Price Tracker

Сервис раз в минуту забирает с криптобиржи [Deribit](https://docs.deribit.com/) индексную цену
`btc_usd` и `eth_usd`, сохраняет её в PostgreSQL и отдаёт сохранённые данные через HTTP API на FastAPI.

- **Сбор цен:** Celery Beat раз в минуту ставит задачу, Celery Worker параллельно запрашивает
  обе цены через асинхронный клиент на `aiohttp` и пишет в базу тикер, цену и время (UNIX timestamp).
- **API:** три GET-метода, у каждого обязательный query-параметр `ticker`.
- **Инфраструктура:** Docker Compose, миграции Alembic, unit- и интеграционные тесты, CI для GitHub и GitLab.

## Архитектура

```
                every 60 s
 ┌───────────┐   task    ┌───────┐   task   ┌──────────────┐  HTTP (aiohttp)  ┌─────────┐
 │Celery Beat├──────────►│ Redis ├─────────►│Celery Worker ├─────────────────►│ Deribit │
 └───────────┘           └───────┘          └──────┬───────┘                  └─────────┘
                                                   │ INSERT
                                                   ▼
 ┌────────┐   GET /prices?ticker=…   ┌─────────┐ SELECT ┌────────────┐
 │ Client ├─────────────────────────►│ FastAPI ├───────►│ PostgreSQL │
 └────────┘                          └─────────┘        └────────────┘
```

Код разложен по слоям, каждый слой знает только о слое ниже:

```
deribit_tracker/
├── config.py            # настройки из переменных окружения (pydantic-settings)
├── domain.py            # Ticker (enum) и PriceSnapshot — общий язык всех слоёв
├── clients/deribit.py   # DeribitClient: только HTTP-общение с биржей
├── repositories/        # PriceRepository: только SQL
├── services/
│   ├── ports.py         # Protocol-интерфейсы, от которых зависят сервисы
│   ├── collector.py     # PriceCollector: получить цены → сохранить
│   └── prices.py        # PriceQueryService: сценарии чтения для API
├── api/                 # FastAPI: фабрика приложения, роуты, схемы, зависимости
├── worker/              # Celery: фабрика приложения, задача, сборка зависимостей
└── db/                  # модель таблицы и создание engine
migrations/              # Alembic
tests/unit/              # без сети и без БД
tests/integration/       # репозиторий на настоящем PostgreSQL
```

## Быстрый старт (Docker)

Нужны Docker и Docker Compose.

```bash
git clone <repo-url> deribit-tracker
cd deribit-tracker
docker compose up --build -d
```

Файл `.env` не обязателен: значения по умолчанию рабочие. Чтобы поменять пароль БД или интервал
сбора, скопируйте `cp .env.example .env` и отредактируйте.

Что произойдёт:

1. поднимутся `postgres` и `redis`;
2. одноразовый контейнер `migrate` применит миграции и завершится;
3. запустятся `api`, `worker` и `beat`;
4. через минуту в базе появятся первые цены.

Проверка:

```bash
docker compose ps                       # migrate — Exited (0), остальные — Up
docker compose logs -f worker           # каждую минуту: Task ... succeeded
curl "http://localhost:8000/prices/latest?ticker=btc_usd"

# заглянуть в базу (порт PostgreSQL наружу не открыт, чтобы не конфликтовать с локальным)
docker compose exec postgres psql -U tracker -d prices -c "select * from prices order by id desc limit 5"
```

Документация API (Swagger): <http://localhost:8000/docs>.

Остановить: `docker compose down` (данные сохраняются в volume `postgres-data`;
`docker compose down -v` удалит и их).

## API

Все методы — `GET`, у всех обязательный параметр `ticker`: `btc_usd` или `eth_usd`.
Время — UNIX timestamp в секундах (UTC).

| Метод | Назначение | Параметры |
|---|---|---|
| `GET /prices` | все сохранённые цены по тикеру, по возрастанию времени | `ticker`, необязательные `limit`, `offset` |
| `GET /prices/latest` | последняя цена | `ticker` |
| `GET /prices/by-date` | цены за период, границы включительно | `ticker`, необязательные `date_from`, `date_to`, `limit`, `offset` |
| `GET /health` | проверка, что сервис жив | — |

Примеры:

```bash
curl "http://localhost:8000/prices?ticker=btc_usd"
curl "http://localhost:8000/prices?ticker=btc_usd&limit=100&offset=200"
curl "http://localhost:8000/prices/latest?ticker=eth_usd"
curl "http://localhost:8000/prices/by-date?ticker=btc_usd&date_from=1791990000&date_to=1791993600"
```

Ответ:

```json
{"ticker": "eth_usd", "price": 2434.47, "timestamp": 1791992264}
```

Ошибки:

| Код | Когда |
|---|---|
| `422` | нет `ticker`, неизвестный тикер, отрицательные `offset`/даты, `limit` < 1, `date_from` > `date_to` |
| `404` | `/prices/latest`, а по тикеру ещё нет ни одной записи |

## Запуск без Docker

Нужны Python 3.12, [uv](https://docs.astral.sh/uv/), запущенные PostgreSQL и Redis.

```bash
uv sync
cp .env.example .env            # укажите хост/порт/пароль своих PostgreSQL и Redis
uv run alembic upgrade head

uv run uvicorn deribit_tracker.api.app:create_app --factory --reload   # API
uv run celery -A deribit_tracker.worker.main worker --loglevel=info    # worker
uv run celery -A deribit_tracker.worker.main beat --loglevel=info      # beat
```

## Тесты и проверки

```bash
make test        # поднимает временный PostgreSQL в Docker (порт 5433) и гоняет все тесты
make test-unit   # только unit-тесты: без Docker, без сети
make lint        # ruff (линтер + форматирование) и mypy --strict
```

Что покрыто:

- **клиент Deribit** — против локального фейкового HTTP-сервера: разбор ответа без потери точности,
  ошибка JSON-RPC, неожиданный формат, 5xx, таймаут, недоступность;
- **сбор цен** — сохранение обеих цен, падение одного тикера не мешает другому;
- **задача Celery** — повтор только для упавших тикеров и только при временных ошибках;
- **сервис чтения** — история, пагинация, последняя цена, диапазон дат, перевёрнутый диапазон;
- **API** — все методы, обязательность и валидация `ticker`, 404, 422, пагинация, диапазоны;
- **репозиторий** — на настоящем PostgreSQL: порядок, фильтры, пагинация, сохранение 8 знаков после запятой.

CI (`.github/workflows/ci.yml` и `.gitlab-ci.yml`) на каждый push запускает линтеры и все тесты
вместе с PostgreSQL.

## Design decisions

### Пять контейнеров вместо двух

В задании предложено развернуть приложение и базу в двух контейнерах. Смысл этого требования —
отделить приложение от базы — соблюдён, но контейнеров больше:

- Celery требует **брокер** сообщений (здесь Redis): Beat кладёт туда задачу, Worker забирает;
- **API, Worker и Beat** — три разных долгоживущих процесса. Принцип «один процесс — один контейнер»
  даёт независимые перезапуски, логи и масштабирование: если упадёт Worker, API продолжит отвечать;
- все три процесса собираются из **одного образа**, отличается только команда запуска;
- `migrate` — одноразовый контейнер: накатывает миграции и завершается, остальные стартуют после него.
  Так миграции не гоняются наперегонки из нескольких процессов.

Уложиться ровно в два контейнера можно (PostgreSQL как брокер, три процесса под супервизором
в одном контейнере), но это хуже по надёжности и прозрачности.

### Почему Celery Beat, а не цикл со `sleep(60)`

Так требует задание, но решение и само по себе оправдано: расписание отделено от исполнения,
есть повторы при ошибках, задачи можно запускать вручную, а Worker'ов — масштабировать.
У расписания задан `expires` равный интервалу: если Worker был недоступен, устаревшие задачи
выбрасываются, а не выполняются пачкой.

### Async-клиент внутри синхронного Celery

Celery выполняет задачи синхронно, а клиент асинхронный (`aiohttp`, как предложено в задании).
Задача вызывает `asyncio.run(...)` — каждый запуск получает новый event loop. Отсюда два следствия:

- обе цены запрашиваются **параллельно** (`asyncio.gather`) в одной HTTP-сессии;
- подключение к БД в задаче создаётся на один запуск с `NullPool` и закрывается в конце.
  Пул соединений asyncpg привязан к event loop, и переиспользование соединений из прошлого
  `asyncio.run` приводит к ошибкам вида «attached to a different loop». В API, где loop один на
  весь процесс, используется обычный пул.

### Обработка ошибок биржи и повторы

- Временные ошибки (сеть, таймаут, HTTP 5xx) — `DeribitUnavailableError`; ошибки ответа
  (JSON-RPC error, неожиданный формат) — `DeribitError`.
- Падение одного тикера не мешает сохранить другой.
- Задача повторяется (до 3 раз, через 5 с) **только для упавших тикеров** и **только при временных
  ошибках**: уже сохранённая цена не задублируется, а на заведомо ошибочный ответ повтор не поможет.

### Хранение цены и времени

- Цена — `NUMERIC(20, 8)` и `Decimal` в коде, а не `float`: деньги не должны терять точность.
  JSON от Deribit разбирается сразу в `Decimal` (`parse_float=Decimal`), поэтому значение сохраняется
  ровно таким, каким его прислала биржа. В ответе API цена отдаётся обычным JSON-числом — так удобнее
  клиентам, а точность хранения от этого не страдает.
- Время — `BIGINT`, UNIX timestamp в секундах, как требует задание. Это **момент получения цены
  нашим сервисом** (UTC), а не время биржи: именно его логично связывать с «текущей ценой на момент
  опроса». Для тестов источник времени подменяется (`clock`).
- Составной индекс `(ticker, timestamp)` — все запросы фильтруют по тикеру и сортируют по времени.
- Схема создаётся миграцией Alembic, а не `create_all()` при старте.

### Контракт API

- `ticker` — `Enum`: неизвестное значение отклоняется на уровне валидации с кодом 422 и понятным
  сообщением, а не доходит до базы.
- **Фильтр по дате** реализован как диапазон `date_from` / `date_to` (UNIX секунды, включительно,
  любую границу можно опустить). Задание формат не уточняет; диапазон покрывает и «один день», и любой
  другой период, а UNIX-время снимает вопрос часовых поясов.
- **Пагинация** `limit` / `offset` необязательна: без `limit` метод возвращает все данные, как и
  требует задание. Но при сборе раз в минуту это 1440 записей в сутки на тикер, и пагинация позволяет
  клиенту не тянуть всё сразу.
- `/prices/latest` без данных отвечает 404, а не `null` — отсутствие ресурса явно.

### Чистая архитектура и отсутствие глобальных переменных

- Слои: клиент → сервисы → репозиторий → API. Сервисы зависят от `Protocol`-интерфейсов
  (`services/ports.py`), а не от конкретных классов, поэтому тестируются с фейками без БД и сети.
- Зависимости передаются явно: через конструкторы и FastAPI `Depends`.
- FastAPI создаётся фабрикой `create_app()`; engine и фабрика сессий живут в `app.state`
  в течение жизни приложения (lifespan).
- Celery тоже создаётся фабрикой `create_celery_app(settings)`. **Единственный объект уровня
  модуля** — `app` в `deribit_tracker/worker/main.py`: CLI Celery (`celery -A ...`) умеет загружать
  только готовый объект из модуля и не вызывает фабрики. Это осознанное и изолированное исключение.
  Остальное на уровне модулей — константы и стандартные `logging.getLogger(__name__)`.

### Инструменты

`uv` (быстрая и воспроизводимая установка по `uv.lock`), `ruff` (линтер и форматтер),
`mypy --strict`, `pytest` + `pytest-asyncio`. Тесты клиента идут против локального HTTP-сервера
на `aiohttp.test_utils`, а не через подмену библиотеки: так проверяется настоящий HTTP-путь.

## Что можно улучшить

- Ограничение уникальности `(ticker, timestamp)` и `INSERT ... ON CONFLICT DO NOTHING` —
  защита от дублей при повторной доставке задачи.
- Курсорная пагинация (`after_timestamp`) вместо `offset` для очень больших объёмов.
- Метрики (Prometheus) и алерт, если цены не поступают дольше N минут.
- Вынести список тикеров в настройки, чтобы добавлять валюты без изменения кода.
- Партиционирование или ретеншн старых данных.
